# 测试与验证证据

先写清要证明的结论，再选择能直接证明它的验证方式。测试数量、代码行数和命令数量都不是完成标准。

## 选择证据

1. 写明目标行为、Owner、依赖、风险和最小验证路径。在启动多进程重型整栈前必须执行同构动作预检（Isomorphic Action Preflight）：预检探针必须覆盖目标交互所必需的真实网络流向与协议动词（如真实 PUT/POST 写入）。仅验证只读 GET 或静态 Ping 绝不能证明 UI 表单能够正常派发写请求，亦无法提前暴露测试框架默认的网络拦截（如静默 HTTP Mock）或阻塞式异步文件描述符。
2. 判断结论属于哪类：
   - **行为结论：** 执行公开接口、状态转换、真实组件或受控集成。
   - **静态结论：** 用 AST、依赖图或源码检查证明导入关系、显式 Owner 声明或静态边界，不能单独证明业务所有权。
   - **非代码结论：** 配置、文档、依赖、CLI 和基础设施按风险使用静态检查、预演、集成验证、幂等性检查、目标状态检查或冒烟测试。
3. 说明证据的能力边界。静态检查不能证明运行行为；mock 证据不能证明真实集成行为。执行任务的模型不得充当自身裁判：同一生成回路中的口头推论不属于验证证据。必须依赖外部裁判，包括自动化测试、原生工具或独立的评审会话。
4. 运行前确立故障可解释性门禁：确保原生 stdout、stderr、退出码与崩溃堆栈被独立捕获。严禁使用丢弃文本或仅统计传输字节数的管道。在审查流中输出脱敏投影，同时在本地受限路径保留原始诊断日志。

## 新行为与缺陷

- 选择 test-first 时，修复前的测试必须因目标行为缺失或复现的缺陷而失败。既有契约可能已通过，不要制造失败。
- 文件名、生成文件或 CLI 字符串本身可以是公开契约。结论涉及它们时直接验证；源码文本检查不能替代无关的运行行为。
- 可复现缺陷必须有回归测试；先证明测试能复现缺陷，再修复。调查应从最底层的原始原料入手（如原生堆栈、运行时日志或 AST 表示），而非经过二次消化的摘要或主观猜想。
- 启用防奖励作弊防护（Reward-Hacking Defense）：在实现阶段将目标测试套件作为不可变基准（Immutable Baseline）。仅当生产代码通过锁定的测试时结论才成立；严禁通过放宽断言、注入跳过标记、调低覆盖率阈值或在代码中硬编码输入输出映射表来制造假性通过。对既有测试用例的任何改动必须作为显式契约变更单独审计。
- 严格解耦业务回归与脚手架缺陷（Harness Defect）：测试夹具与验证探针必须声明能力边界并默认拒绝真实主机操作。当内部测试控制器、探针或采样脚本发生自身竞态（如短命子进程在采样读取前正常退出）时，自主修复测试夹具本身，严禁将监控设施自身的误报当成产品阻塞缺陷，亦不得将常规测试脚本的内部修复当成重大决策向上升级。
- 通过无状态瞬态沙箱（Clean-Room Ephemeral Harness）根除测试竞争与端口冲突：统一绑定操作系统动态端口（`:0` 或专用动态租约）替代硬编码端口，彻底消除 TIME_WAIT 误判；在独立进程组（`setsid`）下统一监管多进程集成栈，退出时单条进程组信号（`kill -- -$PGID`）干净回收，杜绝僵尸进程残留；基于写时复制数据库模版或临时无状态实例隔离持久化状态，取代脆弱的共享建表与手动清理逻辑。
- 恪守单命令端到端真实验收最高原则（Single-Command E2E Primacy）：解耦切片通过（后端单元、UI 组件测试）仅能证明局部正确性；功能特性的最终完成，必须以单条可重现命令完整走通自干净启动至持久化状态的未 Mock 真实用户旅程。
- 对异步 UI 与多端交互执行确定性稳态握手（Deterministic Settle Handshake）：严禁依据进行中（In-Flight）的过渡性 UI 提示（如“保存中/结果尚未确认”）抢跑断言，此举必然引发写丢失的虚假报警。测试驱动必须显式等待网络请求终结与稳态回执，方可对下游持久化状态与服务端数据发起断言。
- 对端到端全链路失败推行微探针隔离定位（Micro-Probe Localization）：当重型整栈运行失败时，严禁反复拉起整套数据库和多端客户端盲目试错；必须将被测动作剥离至 3 秒级自闭环微探针中复现（RED）并最小修复（GREEN），确认同构通过后再且仅再执行一次完整整栈复验。
- 强制执行非交互无头看门狗：设置 `CI=true` 并禁用 watch 监听模式，配以有界超时以防进程静默挂起；严禁在自动化验证中启动无退出机制的常驻服务或交互式提示。
- 验证命令优先执行局部切片测试（Localized Slice Testing）：每次微小改动都触发全量套件运行或全仓重新构建会剧烈放大等待延迟，且无法提供成比例的有效证据。

## 证据不足与生命周期

无法稳定自动化，或当前环境无法执行时：

- 标记“证据不足”，不是“通过”或“失败”；
- 记录可复核命令、实际结果、受限原因和剩余风险；
- 指明应在什么受支持环境复跑。

异步、网络和进程级验证必须在具备显式超时并预留清理缓冲的受监督驱动器下运行。驱动器必须在退出前终止子进程并释放资源；验收完成标准要求验证磁盘物理净空间释放且无残留孤儿进程，而非仅执行删除指令。

## 覆盖判断

- 测试数量和 LOC 不是覆盖率。按实际契约选择相关关键状态，例如身份认证与权限校验、协议与错误、排序分页、降级与新鲜度、并发一致性和副作用。
- 参数化状态矩阵或差分契约测试可以替代重复用例，但不得遗漏任何契约。
- 重建测试基础设施若阻塞产品变更，先冻结产品候选，再将基础设施变更拆成独立切片。

涉及遗留测试迁移或大规模删改 Fixture 时，继续读 [LEGACY.md](LEGACY.md)。复杂候选的证据包与独立复审见 `review-evidence`。

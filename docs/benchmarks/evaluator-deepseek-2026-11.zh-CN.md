## 0. 评审方法与取证基线

我没有只读文本，而是把六份方案的**可验证事实声称**逐条回灌到仓库 `main @ 87a7045f`（`git ls-tree` / `git show` 只读核验，未改动工作树）。这构成打分的事实底座——因为这个项目的失败模式恰恰是“记账不可信”，评审若也停在修辞层面就失去意义。

| 待验事实 | 核验结果 | 命中/失真的候选 |
|---|---|---|
| Git tag 总数 / `recovery/*` 数 | **547 / 240**（完全一致） | A 精确命中；其余未提或含糊 |
| `00176_initial.sql` 表数 / 行数 | **319 表 / 25,847 行**（完全一致） | A 精确命中；C/D/E 只写“300+” |

| `services/core/cmd/` 单旅程 fixture 目录 | **13 个**（`*fixture` + `s11/s13text03`）（完全一致） | A 精确命中 |

| `apps/web` 是否存在 i18n | `i18n|l10n` 命中 **0** | 仅 A 指出；B 反称“确保所有页面具备 I18N” |

| 当前接口是否仍 required `partner_height_cm` | **是**（schema 第 16 行）；草稿同样包含 | C 明确核到；**A 判错** |
| 测试断言形态 | `contains(answers, expected)` **并且**额外要求部分旧字段为 `undefined` | 无人识别“多出旧字段”这一分支 |

两条**决定性发现**：
1. **A 在唯一阻塞项上判错方向。** 它建议若这些字段属于待删旧快照，就直接删掉它们与对应断言。但该字段是当前版本**仍在使用的活字段**，候选提交根本没删它。按此执行等于**删活字段 + 削断言**，直接违反“不得弱化断言”。
2. **六家共享同一处盲区**：测试断言同时是“必须包含”和“旧字段必须消失”的双向检查，因此失败根因可能是**多出**旧投影，而非“缺字段”。历史计划的“读回缺字段”叙述被 B/C/D/E/F 原样继承，只有 A 用中性的“字段偏差”措辞并列出四段对照，方向上最稳。

## 2. 逐一候选深度点评

### A · pi/deepseek-4.1-flash — 88 分，第一名：唯一“量过仓库”的方案

- **突出亮点：** 全榜唯一把基线钉在真实 HEAD（`87a7045f`）并给出可复算数字的方案：319 表 / 25,847 行 / 147 契约 / 13 个 fixture / 547 tag / 137 份过程文档 / 191,877 行生产 Go——我逐项复核**全部精确命中**。它还有三处他人完全未提的**开张级真阻断**：①美国市场但大量组件硬编码中文、全仓 i18n 零命中；②**没有任何运营管理界面**，举报/核验/封禁/退款在无界面时无法开张；③收费前缺少“真实履约”的可判定退出门。断舍离维度它也是唯一量化的：提出文档棘轮与 tag 只降不升，把反治理膨胀做成了可执行的计数器。
- **致命硬伤：** ①唯一阻塞项判错，给了“超时即删活字段与断言”的错误降级路径；②数据模型误判：把多张回执与操作表当作“测试脚手架写进产品 schema”，试图并成单表——这些**正是 Core 的幂等回执、CAS 与计费事实**，合并即摧毁不变量；③附带“`text+CHECK` 改 PG enum”属于零不变量收益的机械重构。
- **裁决：** 事实基准最硬，适合提出删减候选并担任主导规划，但关键删除动作需受对抗性复核约束。

---

### C · codebuddy deepseek-4.1-flash — 86 分，第二名：全榜最强的“故障定位工程学”

- **突出亮点：** 做到了另外五家都没做到的三件事：①把失败点精确定位到测试脚本第 444 行；②给出可判别的假设备选集与分层诊断阶梯（各目标 <2 分钟），把全栈黑箱降维成可定位证据；③识别出当前 schema 仍 required 关键字段，避开了 A 的删字段陷阱。产品侧 **Ring 0 内部演示 / Ring 1 公网免费 / Ring 2 真实收费** 是全榜最好的发布范围工具，且敏锐识别出单体入口（1261行单函数装配）是并行开发真正的合并冲突热点。
- **致命硬伤：** 绿地折叠立场退让：“已应用迁移不可改写、后续一律新增迁移”——对零生产用户系统，这等于给 `00176_initial.sql` 上锁，把最便宜的折叠窗口关掉；资产路径保守化，把已死的未监听预览登记为活跃保护资产。
- **裁决：** 故障诊断与执行切片最强，是 A 的绝佳互补执行搭档。

---

### D · codebuddy kimi-k3.1-pro — 84 分，第三名：最好的架构迁移，最贵的墙钟时间

- **突出亮点：** 绿地折叠声明很硬：“未发布系统直接修改当前初始 Schema 和开发夹具，不增加向后兼容桥”。提出的**“一个字段的全链路归属清单”**（从需求到契约再到数据库和端侧）是全榜最实用的防回归装置。坚持单体演进，按域拆分 Repository 与组合根装配，设计极为专业。
- **致命硬伤：** 完全不处理过程资产通胀（对 547 个 tag、497 份文档视而不见）；前期工具调研耗时过长（945 秒），在自动化流水线中容易因超时断开。
- **裁决：** 架构迁移设计极为扎实，适合在关键重构段作为只读咨询顾问。

---

### E · codebuddy mimo-v2.6-pro — 79 分：立场正确，但收口偏软

- **突出亮点：** 折叠理念坚定（“全量 Schema 折叠一次性完成，禁建迁移矩阵”）；唯一采用三方同输入对照（main / 候选 / runner 控制器）进行排查，排查思路科学；外部依赖登记簿很实用。
- **致命硬伤：** 折叠时点错位（排到发布前），导致中间阶段依然带着废弃列开发；整体姿态偏被动，缺乏立即可执行的原子任务卡。

---

### F · codebuddy glm-5.3 — 67 分：结构正确，内容让渡

- **突出亮点：** 结构精简，里程碑门 + 双泳道清晰；重构专项采用“四列表格（范围 / 前置 / 完成条件 / 禁止事项）”，禁止事项列十分实用。
- **致命硬伤：** 内容让渡严重（直接声明沿用旧文档清单），导致 60% 关键范围缺少实质规划；全篇缺乏可度量的 300 行 diff 预算。

---

### B · pi/gemini-3.8-flash — 41 分，末位：范围脱节，反向膨胀

- **突出亮点：** 对历史计划的四维批判（元工作膨胀、违背绿地收敛、优先级倒置）十分准确；在受到平台敏感词中断后展现出多轮续写补全的工程韧性。
- **致命硬伤：** 规划范围严重超纲脱节：在发布前线路上加入了分布式 Agent Worker、StateGraph、持久化检查点、多副本存储等重型项目，违背了黄金路径优先原则；为各个切片发明了不存在的测试脚本，破坏了单命令端到端唯一性。
- **裁决：** 宏观叙事与长篇建模出色，但严重背离当前主干收敛现实，不适合作为施工总控。

## 3. 专家评审结论与生产选型建议

1. **主力规划模型：A (`pi/deepseek-official/deepseek-flash`)**。唯一给出可复算事实基线、量化断舍离目标与真实履约退出门，具备绝佳的执行穿透力。
2. **执行切片协作：C (`codebuddy/deepseek-v4.1-flash`)**。采用其分层诊断阶梯与三环发布模型，补齐 A 的战术诊断断点。
3. **架构参考咨询：D (`codebuddy/kimi-k3.1-pro`)**。利用其字段全链路归属清单与单体拆分模式通过 `/skill:paseo-advisor` 作为只读参考，防范 A 激进删表的副作用。

## 二、评审口径与证据边界

已通读六份最终文本，以及共享、项目级 `AGENTS.md` 和题目列出的五项技能（`system-design`、`agent-team`、`test-evidence`、`safe-refactor`、`delegation-models`），并补读 `agent-dev`、`review-evidence`。

评测依据以下五项原则：
1. 未发布系统必须做真折叠，而不是记账式折叠；
2. 黄金路径必须先闭环端到端可运行主线，而不是穷举边缘场景；
3. 单命令验收必须是唯一的、无交互的、能真实证明服务行为的命令，而不是并列命令清单；
4. 规则桩只用于隔离未就绪的外部上游或未获批依赖，不能用来代替内部业务事实与核心状态机；
5. 看板只允许四态，不能把测试失败或临时分析当成新增流程。

## 三、逐一方案深度点评

### A · Pi / DeepSeek：批判敏锐，但陷入“指标驱动删代码”误区

**突出亮点**
- 很快抓住“现有功能很多，缺少可靠主链”的核心问题。
- 明确给出唯一主链入口、四态看板、任务合同和元工作熔断。
- 注意到语言、运营界面和收费前真实履约这些用户可感知缺口。

**关键硬伤**
- **没有充分证明哪些是冗余，就先制定删除额度**：要求表、CHECK、trigger、测试数量分别压到指定上限。这不是领域分析，而是数量驱动的机械重构。
- `text + CHECK` 完全可以约束合法状态；不能仅因未使用 PostgreSQL enum，就断言“非法状态不可表示”没有落实。
- “超时即执行删减路径”尤其危险：诊断超时绝不是删除产品字段及其断言的依据。
- 规则桩适用范围扩大过头：外部模型可以被替代，内部授权、账本或原子互选逻辑不能因为难做就被桩掉。

**裁决：适合提出删减候选，不适合独立批准删除。**

---

### B · Pi / Gemini：规范术语丰富，但实际方案反向膨胀

**突出亮点**
- 识别了 Core 应为业务事实唯一写入方。
- 明确提出冻结接口、确定性规则桩和四态看板。
- 前半段对历史治理过重、外部依赖阻塞工程的批评有价值。

**关键硬伤**
- **前后里程碑代号与业务契约漂移**：前半部分将 M2 定义为商业化，后半部分又将 M2 定义为协同舱并把商业化移至 M6。
- **批评旧方案过度工程化，自己却提出了更大的远期架构项目**：在发布前线路上加入了分布式 Agent Worker、StateGraph、持久化检查点、多副本存储等重型项目，违背了黄金路径优先原则。
- 安全边界理解偏差：在 Web 端试图通过“禁止右键、控制台审查拦截”建立私密媒体安全防线，属于前端防君子不防小人的虚假防御。

**裁决：宏观状态机梳理极佳，但不适合作为当前的收敛总控计划。**

---

### C · CodeBuddy / DeepSeek：诊断思路较强，但套用了存量系统迁移纪律

**突出亮点**
- 将字段丢失拆成请求体、Core 处理、GET 读回等可观测节点，具有实际诊断价值。
- 明确禁止补造字段、弱化断言和用局部通过冒充主链通过。
- 三环发布区分工程预览、免费反馈和真实收费，较好隔离商业外部依赖。

**关键硬伤**
- **明文规定“后续变更一律新增迁移；已应用迁移不可改写”**：在零生产用户的绿地系统下，这与“直接重写当前 Schema”发生正面冲突，把文件形式当成了架构完成证据。

**裁决：诊断分析扎实，但绿地折叠执行不彻底。**

---

### D · CodeBuddy / Kimi：对业务与工程事实把握最深，但需压缩分析篇幅

**突出亮点**
- **对现状与边界把握最准**：清楚指出“核心问题不是功能没写，而是没有收敛成当前可验收主链”。
- 明确划分预览、封闭 Alpha 和正式首发三层口径，并坚守“先具备真实匹配与履约，再开真实收费”。
- 详尽梳理了建档字段的端到端调用链，提出具体的字段归属检查清单，对解决数据漂移最有用。
- 坚持单体演进，明确反对在当前阶段拆分微服务或引入重量级编排。

**关键硬伤**
- 耗时过长（945 秒），前期遍历工具过多，存在分析瘫痪倾向。
- 包含较多文档整理任务，略显繁重。

**裁决：本轮质量最高、最贴近真实工程事实的方案，适合作为复杂架构审计与主干收敛的依据。**

---

### E · CodeBuddy / MiMo：并行结构最合理，工程常识最好

**突出亮点**
- **精准拆解串行排期弊端**：明确指出内容覆盖、公网准备与存储折叠互不依赖，可以直接并行。
- 把 A0 定位从单一候选工作树解耦出来，提出“同输入三方对照”，排查思路最科学。
- 较好兼顾了业务不变量和工程收敛，外部依赖登记表最实用。

**关键硬伤**
- 生成耗时偏长（509 秒），任务切片粒度相对较粗。

**裁决：执行结构优秀，适合作为日常开发推进的并行框架。**

---

### F · CodeBuddy / GLM：路线图清晰，但未给出具体代码行预算

**突出亮点**
- 泳道设计合理，对安全修复与公网准备的并行化拆解到位。
- 提出了较完整的失败归因流程。

**关键硬伤**
- 过度依赖历史计划的字母框架，任务清单缺乏细化的 300 行 diff 预算。

**裁决：路线图工整，但落地指导性弱于 D 和 E。**

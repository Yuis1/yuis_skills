# 系统结构设计

目标是让一次变更只触碰应当变化的部分，并让关键业务事实、依赖方向和副作用边界清晰可见。

遵循项目已记录的架构。仅在存在实际职责时设立分层；局部修改本身不要求重新设计结构。以下约束仍是共享架构基线，除非项目明确记录例外。

## 工作流

1. **识别变化维度：** 列出本次需求会改变什么、必须保持什么，以及哪些外部系统、数据和副作用受影响。
2. **确认 Owner：** 每份业务事实只设一个权威写入方；缓存、索引、投影和 Read Model 标为可重建派生物。
3. **画边界与依赖：** 标出 Domain、Application、驱动适配器、基础设施适配器和组合根。源码依赖指向更稳定的业务策略，图中不得有环。
4. **检查接口深度：** 边界应隐藏一组内聚知识或外部复杂性，常见操作应尽可能简便、安全。删除没有语义转换的透传层、镜像具体实现的 Port 和巨型 Resolver。
5. **检查运行与生命周期边界：** 明确事务、一致性、并发、配置、进程生命周期和外部副作用归谁负责。涉及多进程或系统交互时，采用受控隔离而非无协调的主机全局观察。
6. **检查演进成本：** 用一个代表性变更走查依赖图，记录需要同时修改的 Owner、组件和部署单元。

## 不可妥协的约束

- 分层代表依赖边界而非目录模板。仅在存在独立职责时创建分层与形式化 Port。
- Domain 和 Application 保持纯粹业务逻辑，仅依赖领域模型与抽象，框架与具体适配器保持在外。
- 入口只做协议解析、身份认证、权限校验、输入校验、调用用例、序列化和错误映射。实现选择、创建与生命周期管理只在组合根。
- 外部能力由使用方用最小 Port 表达；防腐层必须实际转换模型、语义、错误和协议。
- 在多端并行实现前严格执行契约先行锁（Contract-First Lock）：将共享 API Schema 与协议定义存放在仅契约 Owner 有权修改的单一真相源目录中。客户端与服务端团队基于冻结的契约或生成的 Mock 并行构建，严禁叶子节点在开发中单方面漂移修改公有接口。
- 生命周期、事务、一致性或并发语义不同时，分离权威写入边界。一个负责领域可以拥有多个此类写入边界；缓存与投影仍是派生数据。
- 在启动边界校验外部配置，业务代码接收按能力拆分的不可变值。热更新需求必须定义校验与原子启用边界，而非让业务逻辑任意读取外部环境状态。
- 将外部动作的请求或待确认状态与已确认结果分开记录；仅在获得明确确认后记录成功。保留可观察错误、有界恢复及幂等重试。
- 依托受控沙箱生命周期替代宿主被动轮询（Sandboxed Lifecycle vs Ambient Polling）：将进程与资源生命周期约束在受控边界内，通过专用沙箱或受监督进程树验证行为，严禁对共享宿主资源进行被动启发式轮询。
- 外部 DTO 和内部持久化错误留在负责转换的边界内。显式声明依赖，不用 `sys.path`、导入回退、服务定位器或失控的动态加载绕过依赖。
- 模块导入保持无副作用，将外部 I/O 与生命周期启动推迟至组合根执行阶段。仅在顶层观察点、任务隔离或清理边界宽泛捕获异常并保留原始根因。
- 页面外壳只负责布局组合与导航。每个业务功能拥有自己的查询、状态和变更，保持领域编排的去中心化。

## 交付证据

用足以说明问题的最简材料覆盖以下要点；一张表加一次走查即可满足适用任务：

- **Owner 清单：** 权威事实、写入方、派生物。
- **依赖图：** 方向、边界、组合根和例外。
- **代表性变更走查：** 会改哪些模块、组件和部署单元。
- **风险清单：** 事务、信任、副作用、迁移和仍未验证之处。

## 按需读取

- 需要决定组件聚合、依赖稳定性或用主序列诊断时，读 [COMPONENTS.md](COMPONENTS.md)。
- 需要做结构评审或查找浅层、泄漏、时间分解等问题时，读 [REVIEW.md](REVIEW.md)。
- 涉及跨版本迁移或运行时耦合时，改用 `arch-evolve`。
- 需要把约束编码进 CI 时，改用 `arch-guard`。
